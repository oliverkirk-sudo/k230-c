## Highest-consequence findings

### eMMC rail-name reversal was real and is corrected in this snapshot

The original inspected v4 generator assigned Samsung **VDD to VDD_3V3** and **VDDF to VEMMC_IO**. Exact Samsung part-family documentation, page 4 table 1 and page 5, specifies **VDD = VCCQ (interface/controller)** and **VDDF = VCC (flash)**. The intended fixed-1.8-V HS200 I/O mode therefore made that mapping erroneous. The parent corrected the mapping during this review; this frozen XML now puts C6/M4/N4/P3/P5 on VEMMC_IO and E6/F5/J10/K9 on VDD_3V3. The corrected VEMMC_IO net is still source-less. Merely correcting names or adding power flags cannot make storage operational.

### H5 is legitimately unused for HS200; B6 still needs a pad policy

Samsung's H5 Data Strobe is a device-generated HS400 output. It is not required by the selected K230 HS200 path. H5 should not be wired around the three-switch isolation architecture merely to reduce ERC. An intentional-unused output annotation is supportable for a firmware-enforced HS200-only design. It is not an intrinsic NC ball.

K230 B6 MMC0_STROBE is an **input**, per official pinout row 28. The TRM, PDF page 963, gives STBPAD_CNFG at PHY+0xA a reset value of 0x0440; WEAKPULL_EN[4:3] resets to 0, meaning neither pull is enabled. CanMV U-Boot programs field value 2 (pull-down) for both the SD and eMMC pad modes, but only after code reaches pad initialization. This does not establish BootROM or reset-time behavior. Preserve the warning until that policy is verified. Do not borrow a TI host's internal-pull guarantee, ground B6 arbitrarily, or call B6 a physical NC.

### K230 unused analog pins require individual treatment

U6 MIPI_ATB has explicit manufacturer guidance permitting floating when unused (official pinout row 506 and Hardware Design Guide MIPI section). It was already handled before this baseline, so it is not one of the 51 violations.

D8 ANA_TS_VTEST is an **output** in official pinout row 78 and TRM section 2.10.6. The Canaan reference page 1 and 01studio page 1 leave it open; the actual endpoint was visually checked. That supports a reference-level unused-output disposition, subject to reviewer acceptance. It does not justify grounding it or changing it to an intrinsic no-connect type. No generic rule permitting every unused K230 analog pin to float was found. The guide's permission to omit supplies for an unused peripheral is also not an exemption for ADC/CODEC interfaces required by the replacement-module contract.

### PMU cold start is a specification dependency, not harmless spare I/O

TRM section 14.3, PDF p1169, identifies PAD64/INT0 long-press or PAD68/INT4 high level as the cold-start event. PAD70 then enables external power, PAD71 releases reset about 50 ms later, and Normal-to-PMU isolation is removed about 60 ms after PAD70 enables. PMU-to-Normal access also requires sysctl ISO control. The official default-state sheet specifies pull-down on all four current open PMU pins. Leaving INT0 and INT4 open does not provide either trigger. The present externally enabled regulators may power the CPU independently, but that does not prove PMU-domain access or the private PMU-GPIO regulator buses operate. Keep C10/C12/B11/C11 as unresolved endpoints until the startup or bypass/isolation strategy is demonstrated. Do not infer safe unused status solely from a reference board's open pads.

### PAD68 automatic-start candidate and timing correction

The default register fields support **active-high level detection** on PAD68/INT4/C12, rather than requiring a later rising edge:

| Register | Reset / relevant field | Interpretation |
| --- | --- | --- |
| PMU_INT_DETECT_EN, offset 0x004C | 0x810, bit 4 = 1 | INT4 detection enabled at reset |
| PMU_INT_DETECT_TYP, offset 0x0050 | 0x0, bit 5 = 0; bit 3 = 0 | INT4 effective level is high; detection is level-triggered |
| PMU_IO_CFG_4, offset 0x0090 | 0x1124 | PAD68 starts in PMU function with input enabled, output disabled and pull-down enabled |
| PMU_INT0_TO_CTL_REGISTER / PMU_INT1_TO_CTL_REGISTER | offsets 0x0040/0x0044, reset 0xFFF; bit 4 = 1 | INT4 participates in the reset-default OR routing to PAD70/PAD71 control |
| PMU_OUT_DELAY_SET, offset 0x007C | 0x01100640 | PAD70 event delay disabled; PAD71 logic delay enabled, nominal 0x640 32-kHz ticks |
| PMU_NORMAL_TIMER_VAL, offset 0x00A0 | 0x780 | Nominal 60-ms core-stability/isolation timer |

Evidence: TRM PDF pp1172-1176 and pp1179-1181. C12's official supply domain is AVDD1P8_LDO, which is now on the shared AVDD1P8_PMU filtered domain. A pull-up from that same domain is a plausible automatic-start candidate. No resistor value or new wire is approved by this review: input VIH, internal pull-down tolerance, power-rise behavior, permitted leakage, startup/shutdown control ownership, and private regulator-bus access need verification. Do not pull it to 3.3 V, arbitrarily reinterpret it as NC, or assume a permanent high produces a complete safe power sequence.

The actual TRM **cold-reset flow figure on PDF p1183**, visually inspected, includes **about 1000 ms for initial PMU oscillator stabilization** before waiting for a wake event, then nominal 50 ms for core clock/POR stability and about 9 ms of hardware boot. These are descriptive timings, not complete guaranteed min/max limits. The section 14.3 narrative places both the approximately 50-ms PAD71 reset release and approximately 60-ms Normal-to-PMU isolation removal relative to PAD70 enabling; it does **not** justify adding them into a fixed 110-ms reset delay. A fixed 110-ms delay from rail rise also ignores the initial oscillator step. Use a proved readiness/reset strategy and verified worst-case timing in the next design stage.

The Canaan and 01studio reference page-1 PMU regions were visually checked: both leave C12, C10, B11 and C11 unconnected. They do not provide a precedent for a PAD68 pull-up, nor prove that the new private PMU-GPIO I2C regulator scheme works with those pins open. The reference designs can inform topology without being substituted for the new design's startup/isolation validation. Current CAD remains frozen at the separately verified 14-violation export above.

### Mode-specific non-use is not an intrinsically NC package pin

The official pinout identifies the nine DDR balls C20/D19/D20/F18/G17/H18/H19/M17/N18 as NC in both LP3 and LP4. K20/L17/L18/L20/M20 instead have LP3 CA/ODT functions and are unused only in LP4; M20's historical DDR_NA spelling is resolved by the official DDR_CA2_NC entry. Preserve the functional identity and explicit LP4 mode on those five.

J17/J19/P18/T19 are real rank1 CKE/CS functions. The official LP4 Figure 3-12 leaves them open. The chosen Samsung device's page 10 ballout and page 11 block diagram expose only one CS/CKE pair per channel: H4/J4 for A and R4/P4 for B. The existing 65-net mapping connects those through rank0. If intentional-unused markers are applied, retain functional pin types and ensure firmware does not enable a second rank. Do not infer non-use just because a multi-mode name contains “NC”.

## Issues ERC does not prove away

- GLOBAL_DISABLE still lacks a validated pre-ROM release generator. Its pull-up creates a defined static disabled state, so an ordinary “unconnected” check need not flag the fact that the storage path never becomes usable. The selected bus must be enabled before the ROM reads the storage that loads later software.
- Source-less VEMMC_IO is only the visible part of the cold eMMC/TF voltage gate. Correct fixed flash VCC, first-drive signaling, no unselected-device exposure, reset collapse behavior and ROM boot-device support all need proof.
- The six bank nets are real carrier inputs in the candidate contract. A passive J1 pin does not itself prove module power direction, allowable backfeed, or the CORE-before-bank timing requirement. Keep them distinct until that contract is resolved.
- A passive path to a regulator is connectivity evidence only. Inductor/MLCC effective values, feedback accuracy, DCR drops, regulator headroom, enable/PG behavior, full startup/shutdown/brownout ordering, decoupling placement, SI/PI and thermal/current validation remain release gates.
- Most signal pins use conservative bidirectional review types. A clean(er) ERC would not constitute correct-direction, safe-voltage, high-speed timing, boot-firmware or fabrication sign-off.
- No footprints, PCB routing or manufactured electrical behavior were checked by this triage. Do not turn evidence-backed annotation into a claim of a fabrication-ready design.
